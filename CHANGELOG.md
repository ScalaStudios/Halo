# Changelog

All notable changes to Halo are recorded in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Halo has not published a release yet; versions will follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html) once it does.

## Unreleased

### Added

- Sign-in without passwords: passkeys and security keys (WebAuthn discoverable credentials), authenticator apps (TOTP), and single-use recovery codes.
- Invite and reset links that work once and expire after the setup link lifetime, 7 days by default, and resetting a person's authentication from the console.
- Email over SMTP for invitations, resets, magic links and access request notices, with an outbox in the database, retries, and `GET /api/v1/dev/outbox` in development.
- Magic sign-in links that work once for 10 minutes, limited to 5 per person in 15 minutes.
- Email sign-in codes as an alternative to magic links: an organization setting under Methods chooses whether sign-in emails hold a link, a six-digit code or both. People enter the code on the sign-in page that asked for it, so they can read the email on any device. Codes share the magic link rate limit, are stored as keyed hashes, allow 5 attempts, and failed codes count toward the lockout.
- Federated sign-in with Google, Microsoft Entra ID, GitHub and generic OpenID Connect providers: PKCE, verified email matching, allowed email domains, accounts created on first sign-in with default groups, and linked accounts people can unlink in the account portal.
- OpenID Connect provider: authorization code flow with PKCE (required for single-page and native applications), refresh tokens with rotation, client credentials for service applications, userinfo, token introspection and revocation, RP-initiated logout that ends the Halo session, discovery and signing keys. ID tokens are signed with RS256 and carry a `groups` claim with the names of the person's groups, and a `picture` claim with the person's profile picture when they have one and the application requests the `profile` scope.
- Profile pictures people and user administrators set from the account portal or the console. Halo stores them in PostgreSQL, or in an S3-compatible bucket (`HALO_S3_ENDPOINT` and the related variables) such as Cloudflare R2, Backblaze B2, iDrive e2 or MinIO. SAML assertions include the same URL as a `picture` attribute, and outbound SCIM sends it as the user's photo.
- Application logos that application administrators upload on the application's page or with `PUT /api/v1/applications/{id}/logo`: PNG, JPEG, WebP or SVG up to 512 KB, stored like profile pictures. The console, the account portal and the sign-in page show them, or the application's initials when there is none.
- `prompt=login`, `prompt=none` and `max_age`, and a completed sign-in can only be redeemed in the browser session that completed it.
- Sign-in frequency for each OpenID Connect and SAML application, on its Authentication tab or as `maxAuthAge` on `PATCH /api/v1/applications/{id}`: people who signed in to Halo longer ago than that sign in again before the application gets a code, an assertion or a device approval, `prompt=none` returns `login_required`, and its refresh tokens stop working, while other applications keep single sign-on. Token lifetimes don't change, so access tokens already issued last until they expire. Changes are in the audit log.
- SAML 2.0 identity provider: metadata, SP- and IdP-initiated sign-in, signed assertions, NameID formats, attribute names, and service provider metadata import, with guides for AWS IAM Identity Center and Slack and an example service provider in `examples/go-saml-sp`.
- Encrypted SAML assertions: each SAML application can encrypt its signed assertion with AES-256-GCM, or AES-256-CBC for older service providers, with the key sent by RSA-OAEP to the service provider's encryption certificate. Halo imports the certificate from the service provider's metadata, picking the one that expires last during a rollover, or takes it pasted on the application's Authentication tab, and refuses certificates that are unreadable, not RSA of at least 2048 bits, or expired.
- API resources: your own APIs with scopes, identifiers and token lifetimes, grants to applications, the `resource` parameter, and JWT access tokens with the API in `aud`.
- ES256 and EdDSA (Ed25519) signing next to RS256: each application picks the algorithm of its ID tokens on its Authentication tab, or with `id_token_signed_response_alg` in dynamic client registration, and each API resource picks the algorithm of its access tokens. RS256 stays the default. Halo creates the first key of an algorithm when it first signs with it, publishes every key in the JWKS with its `alg`, advertises all three in `id_token_signing_alg_values_supported`, and rotates and retires the keys of each algorithm on their own. A token request for APIs with different algorithms fails with `invalid_target`.
- Token exchange (RFC 8693): web and service applications with token exchange turned on in their authentication settings trade a person's access token for a narrower one to an API they have scopes on, with the API in `aud`, as long as the original token was issued for one of the APIs the application accepts tokens from, the application in the `act` claim, a lifetime no longer than the original token's, and a `token.exchange` audit event for each exchange.
- Dynamic client registration (RFC 7591) at `/oauth2/register`, off by default and advertised in discovery when on: security administrators choose under Security defaults whether anyone, clients with an initial access token (an API key with the new `registration` scope), or anyone after approval can register. Registered clients use the authorization code flow with PKCE or a client secret, get only the `openid`, `profile` and `email` scopes, no groups, API grants or token exchange, and read, replace or delete their registration with their registration access token (RFC 7592). With approval, new clients stay disabled until an application administrator approves them, and a client that changes its registration waits for approval again whenever approval is on or it is assigned to groups. The console marks them as registered dynamically, and registrations, changes, approvals and deletions are in the audit log.
- Consent screen for third-party applications: an application with the consent screen turned on, which clients that register themselves get by default, shows people its name, logo, website and the requested scopes in plain words before their first sign-in and again when it asks for more, and any OpenID Connect application that sends `prompt=consent` gets it too. Allowed scopes are remembered per person and application, `prompt=none` returns `consent_required` until they are, and declining returns `access_denied` and writes an interrupted event to the sign-in log. People see and remove the access they allowed under Applications in the account portal, which revokes that application's tokens. Grants and removals are in the audit log, and the sign-in page refuses to load in a frame.
- Access policies: conditions on people, groups, applications, network zones, device trust, sign-in risk and sign-in method; allow, block and require-a-passkey effects; report-only mode with 24-hour activity; and a simulator.
- Terms of use: documents with a name, text or a link, and a version that goes up when the text or link changes; a "Require accepting terms of use" policy effect; acceptance once per version at sign-in or under Terms in the account portal, asked again after a new version; and each acceptance with its time and version in the JSON export.
- Network zones, device tracking with trust levels, sign-in risk signals (risky network, repeated failures, new device, new network, password), and risk events that security administrators resolve or dismiss.
- Turning sign-in methods on and off for the organization.
- Passwords as an optional sign-in method, off by default and turned on under Methods after a warning: Argon2id hashing, 15 to 256 characters with no composition rules, a Have I Been Pwned range check that can be turned off, an authenticator code required by default, limits to chosen groups, failed passwords counted toward the lockout and, at 4 times the lockout threshold within the window, refused from the same IP address across all accounts, temporary passwords that administrators set and people change at their next sign-in, a reminder in the account portal to add a passkey, and an `amr` claim of `pwd`, or `pwd otp mfa` when an authenticator code was also entered.
- Group owners and self-service membership: user administrators name owners for assigned groups, owners add and remove members and approve requests to join from the Groups page of the account portal or `POST`/`DELETE /api/v1/groups/{id}/members` without an administrator role, each group is closed, open on request or open to anyone, people join or ask from the account portal, owner actions are in the audit log, and the access review dialog can add the group's owners as reviewers. Rule-based groups cannot have owners.
- Access packages with approvers, maximum durations and justifications; access requests with email notices, approval, denial, cancellation, expiry and revocation; access reviews with automatic removal and overdue tracking; and joiner, mover and leaver lifecycle rules with run history.
- Just-in-time administrator roles: global administrators make people eligible for a role under Roles, and eligible people activate it under Access in the account portal for 1 to 8 hours with a reason, can deactivate it early, and lose it on the first request after it ends; eligibility, activation, deactivation and expiry are written to the audit log, nobody can make themselves eligible or give themselves a role they activated, and eligible people are protected like administrators.
- Service accounts with roles and owners, and API keys with `api` and `scim` scopes and optional expiry.
- SCIM 2.0 server under `/scim/v2` for users and assigned groups, tested against the Okta and Microsoft Entra ID request shapes.
- Rate limits per API key and per session: 600 requests a minute for each API key by default, set per service account, 1,200 for each session, and 3,000 for each API key on SCIM, counted apart. Responses carry `RateLimit-Policy` and `RateLimit` headers, requests over the limit get `429` with `ERR_RATE_LIMITED` and `Retry-After`, and the console shows each key's rejected requests from the last 24 hours.
- Outbound SCIM provisioning that creates, updates and deactivates the people assigned to an application every 2 minutes or on demand.
- Audit events for changes to users, roles, groups, applications, access policies and settings record each changed field with its old and new value, shown as a diff when you open an event in the audit log and included in `GET /api/v1/audit`, webhooks and the JSON export. Secrets such as the bot protection secret key are marked as changed and their values are never recorded.
- Webhooks for audit and sign-in events, signed with HMAC-SHA256, with retries and a delivery log. Endpoints receive every event, whole families such as `user.*`, or single event types such as `user.suspend`, chosen from a searchable list that describes each type. `GET /api/v1/webhooks/event-types` returns each family with its event types and their descriptions.
- SSH certificate authority with group-to-principal mappings and a configurable certificate lifetime.
- The `halo` client commands `login` (device flow), `whoami`, `ssh-cert` and `logout`, and the built-in Halo CLI application.
- Organization settings: name, contact email, sign-in message, logo, session lifetime, lockout, setup link lifetime and token lifetime defaults.
- Branding colours for the sign-in, setup and account pages: accent, background, surface, border, text and link, with a live preview, contrast warnings and a reset to Halo's colours.
- Email templates under Settings: global administrators change the subject and body of the invitation, authentication reset, sign-in link, sign-in code and access request emails, with a live preview, a reset to Halo's default, and `email_template.update` and `email_template.reset` audit events. Templates use `{{.Variable}}` and `{{if .Variable}}…{{else}}…{{end}}` with the variables each email lists; anything else, and unknown variables, are refused on save. Values such as names are inserted as plain text and never run as template code, and the JSON export includes the templates.
- Custom CSS after Halo's stylesheet on the same pages, and optionally in the admin console: up to 32 KB, changed only by global administrators, and turned off with `HALO_DISABLE_CUSTOM_CSS=1`.
- A Content Security Policy on every page, so images, fonts, stylesheets and scripts load only from Halo's own address.
- Domain verification with DNS TXT records, and a JSON export of users, groups, memberships, roles, applications, policies, access packages and access reviews.
- Administration console: overview, users with profile editing, assigned and rule-based groups with rule preview, service accounts, devices, applications with editable redirect URIs, scopes and token lifetimes, API resources, provisioning, roles, policies, infrastructure access, governance, methods, identity providers, sessions, sign-in log, audit log, risk events, API keys, webhooks and settings.
- Applications: client secrets shown once, rotation with a 24-hour grace period, revocation, enabling and disabling, group assignment, owners, and setup guides for Grafana, Forgejo, kubectl, generic OpenID Connect, generic SAML, AWS IAM Identity Center and Slack.
- Account portal: profile, passkeys, security keys, authenticator apps, recovery codes, linked accounts, sessions, applications, access requests, approvals, access reviews and activity.
- Management API under `/api/v1` with administrative roles: global, security, user, helpdesk and application administrator, and auditor. Every administrative change writes an audit event in the same transaction. The OpenAPI 3.1 document is served at `/api/v1/openapi.yaml`.
- A Terraform and OpenTofu provider in `cmd/terraform-provider-halo` for users, groups, group memberships, OpenID Connect and OAuth applications, access policies and API resources, with an example in `examples/terraform`.
- `HALO_TRUSTED_PROXIES` for client IP addresses behind reverse proxies.
- Signing key rotation: new OpenID Connect keys sign immediately while previous keys stay in the JWKS for 7 days, and new SAML certificates are listed beside the previous one until it is removed.
- `email_verified` in ID tokens and userinfo, set when a person redeems an emailed link or signs in through a provider that verified the address, and cleared when the address changes.
- Sessions bound to the device that started them: blocking a device signs it out. Halo CLI sessions appear in the account portal and the console and can be signed out like browser sessions.
- A per-address limit on device authorization requests and `slow_down` for clients that poll too fast.
- The `halo` command: `serve`, `migrate`, `bootstrap`, `seed-demo`, `dev-session` and `rotate-secret-key`, which re-seals every stored secret under a new `HALO_SECRET_KEY`.
- The Fernway Systems demo organization, loaded with `halo seed-demo`, with data for every area of the console.
- An example Go web application that signs in with Halo, in `examples/go-web-client`.
- End-to-end tests with a virtual authenticator for passkey sign-in to the OpenID Connect and SAML examples, magic links, access requests, access policies, and every console page at desktop and phone widths.
- Docker images for the server and the web interface, and a Docker Compose deployment with PostgreSQL and Caddy, in `deploy/`.
- Container images for `linux/amd64` and `linux/arm64`, published to `ghcr.io/scalastudios/halo-server` and `halo-web` for every commit on `main` and every release tag. The Compose deployment uses them, and `deploy/compose.build.yml` builds from the checkout instead.
- An install script, `deploy/install.sh`, behind `curl -fsSL https://halo.scala.gg/install.sh | sh`, that sets up the Docker Compose deployment on a fresh host, installing Docker first when it is missing, and stays on the host as `halo.sh` to create the first administrator, start, stop, restart, update and follow logs.
- A Helm chart in `deploy/helm/halo` for the server and the web interface, with an optional Ingress, an optional PostgreSQL StatefulSet, secrets read from existing Kubernetes Secrets, and non-root pods with read-only root filesystems.
- A console home page with the organization's directory counts, your roles, open risk events and shortcuts, above what needs attention.
- Bookmarks: links such as an intranet page, status page or helpdesk that open from the account portal, with a name, a logo and a URL, assigned to groups like applications, and no sign-in protocol.
- Collections: named sections of the account portal, such as Engineering or HR, that application administrators create under Applications and assign to groups. People see only the applications in a collection that they can already open.
- Favourites and a personal order in the account portal: people mark applications as favourites, which appear first, and move applications earlier or later. `PUT /api/v1/me/applications` saves both, and `GET /api/v1/me/collections` lists a person's collections.
- Changing a person's administrator roles from their page in the console, and an optional role when inviting them. Both need a global administrator, like the Roles page.
- User and operator documentation at [halo.scala.gg/docs](https://halo.scala.gg/docs), with guides for email, policies, governance, federation, provisioning, webhooks, API resources and infrastructure access, and integration guides for Grafana, Forgejo, Nextcloud, Kubernetes, Proxmox VE, Outline, Headscale, AWS IAM Identity Center and Slack.
- Continuous integration for `go vet`, `go test`, type checking and the web build.
- Contributing guide, security policy, code of conduct, and issue and pull request templates.
- A limit on how many sessions one person can hold at once, set under Security defaults for the organization and per group, where someone in several limited groups gets the lowest limit. At the limit Halo either refuses the new sign-in with `ERR_SESSION_LIMIT` or ends the oldest sessions, and records each ended session in the sign-in log with the result `ended` and the `sign_in.ended` webhook event. Halo CLI sessions are either counted separately against the same limit or not limited.
- Approval by a second global administrator, off by default, for granting the global administrator role or making someone eligible to activate it, stopping an enforced access policy, turning on password sign-in and changing identity providers. The change waits on the Approvals page for 72 hours; the requester cannot approve it, approving applies it once as the requester, and a request whose target changed in the meantime is not applied. Emergency access accounts skip approval, and each use is emailed to the other global administrators. Requests, approvals, rejections, approved changes that could not be applied, and skips are in the audit log.
- Bot protection with Cloudflare Turnstile or hCaptcha, off by default and set under Security defaults with a site key and an encrypted secret key. The sign-in page asks for the check before Halo emails a sign-in link or code, and before passwords and codes from an IP address that reached the lockout threshold; passkeys are never checked. Halo verifies every check with the provider and refuses the request when the provider can't be reached. Failed and unverifiable checks are in the sign-in log and do not count toward an account's lockout.
- Retention periods for the sign-in log and the audit log, set by a global administrator under Organization. Both keep entries forever by default. Once a day Halo deletes entries older than the period in batches of 5,000 and records how many it deleted in the audit log.
- Re-authentication before sensitive changes: granting or activating administrator roles, creating service accounts and API keys, rotating signing keys, SAML certificates and client secrets, changing access policies, sign-in methods, organization settings and identity providers, resetting another person's sign-in methods, exporting the configuration and approving a held change need a sign-in with a passkey, security key or recovery code within the last 10 minutes, set under Security defaults. Otherwise the console asks the person to confirm with their passkey, or their authenticator app when they have no passkey, and then makes the change; confirmations are in the audit log as `user.reauthenticate`. Adding or removing your own passkey or authenticator app and creating recovery codes ask too once you have one. A sign-in with a recovery code counts as recent, so someone who lost their passkey can still set up a new one. API keys are not affected, and approved changes apply without asking the requester again.

### Changed

- Pages in the console and the account portal show a skeleton of their layout and a thin progress bar at the top as soon as you navigate, and the console home page fills in each card as its data arrives. Buttons stay busy until the updated page is on screen, so an action can't be sent twice, and when an action fails its error appears next to it. The command palette tells screen readers which result is highlighted.
- Assigning groups to an application and adding a person to groups open a searchable dialog instead of a menu. It shows each group's member count and whether it is rule-based, marks groups that are already assigned, and adds several groups at once.
- Recovery codes are 16 characters (80 bits) and stored as HMAC-SHA256 with a key derived from `HALO_SECRET_KEY`. Migration `0010_hardening` deletes codes generated by earlier development builds; generate new ones from the account portal.
